# Releases and versions

How releases are versioned, what they contain, and how to verify them
before you install.

:::{important}
The newest release is `v0.1.0-rc.1`, a release candidate. See
[Installation](../getting-started/installation.md).
:::

## Versioning

- **SemVer.** Releases are named `vX.Y.Z`, pre-releases `vX.Y.Z-rc.N`.
- **Signed tags.** Maintainers cut a release with a signed annotated tag,
  `git tag -s vX.Y.Z`. The release workflow accepts only a tag at the
  checked-out commit with a good OpenPGP signature from one of the
  maintainer keys; without a valid signature, nothing is published.
- **Changelog.** The release notes on GitHub group the commits by their
  subsystem prefix, the same prefixes that
  [Contributing](contributing.md) lists.

## What a release contains

For `amd64` and `arm64`:

| Artifact | Name |
|---|---|
| Archive | `lazysubmodules_<version>_linux_<arch>.tar.gz`, with the binary, `LICENSE`, `README.md`, `THIRD_PARTY_NOTICES` and `licenses/` |
| Debian package | `lazysubmodules_<version>_linux_<arch>.deb` |
| RPM package | `lazysubmodules_<version>_linux_<arch>.rpm` |
| SBOM | `<archive>.sbom.json`, an SPDX document generated by syft |
| Checksums | `checksums.txt` (SHA-256) for all archives, packages and SBOMs |
| Signature | `checksums.txt.sig` and the certificate `checksums.txt.pem`, plus the same signature as the Sigstore bundle `checksums.txt.sigstore.json` |

The archives and packages are not signed themselves. Their integrity
comes from the signed `checksums.txt`.

The binaries are reproducible in the sense that a rebuild of the same
commit gives the same result: the version, the commit and the commit date
are injected at build time, and the commit date is used rather than the
build date.

## Verify a download

The checksums are signed with [cosign](https://github.com/sigstore/cosign)
keyless signing from the release workflow. Verify the signature, then
check the files against the checksums:

```sh
VERSION=0.1.0-rc.1
BASE="https://github.com/FPGArtktic/lazysubmodules/releases/download/v${VERSION}"
for f in checksums.txt checksums.txt.sig checksums.txt.pem; do
	curl -fLO "${BASE}/${f}"
done

cosign verify-blob \
	--certificate checksums.txt.pem \
	--signature checksums.txt.sig \
	--certificate-identity-regexp '^https://github\.com/FPGArtktic/lazysubmodules/\.github/workflows/release\.yml@refs/tags/v.+$' \
	--certificate-oidc-issuer https://token.actions.githubusercontent.com \
	checksums.txt

# Then check the downloaded archives and packages against the checksums.
sha256sum --ignore-missing -c checksums.txt
```

- **Result:** cosign prints `Verified OK` on success.
- **Identity:** the regular expression ties the signature to the release
  workflow of this repository, running on a tag. Do not weaken it.
- **Bundle:** with a recent cosign, `--bundle checksums.txt.sigstore.json`
  can replace `--certificate` and `--signature`.
- **Network:** verification looks up the signature in the public Sigstore
  transparency log, so it needs network access.
- **Deprecation warnings:** recent cosign versions warn that
  `--certificate` and `--signature` are deprecated. The flags still work.

### Verify a release tag

Release tags are signed as well. With the maintainer's public key in your
keyring:

```sh
git tag -v v0.1.0-rc.1
```

## Version of an installed binary

```sh
lazysubmodules version
```

The output names the version, the source commit and the date of that
commit, in UTC. It is not the build date, so a rebuild of the same commit
prints the same. What the fields contain depends on how the binary was
built; {ref}`ref-cli-version-builds` lists every case.

Include this output in bug reports and in security reports.

## Supported versions

Security fixes go into a new release; older releases do not get fixes.
See the [Security policy](security.md) for the supported versions and how
to report a vulnerability.
